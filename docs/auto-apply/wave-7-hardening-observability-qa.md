## Ordered tickets

1. **`AJA-OBS-001`** — Metrics, audit events, and alerts.
   Emit metrics/events for: plans created, approvals, submissions by channel, unknown-outcome count, duplicates prevented, consent revocations, queue depth. Wire alerts for unusual spikes in `SUBMISSION_OUTCOME_UNKNOWN` or `FAILED_DO_NOT_RETRY`.

2. **`AJA-OBS-002`** — Admin diagnostics for stuck/unknown submissions.
   An admin-facing view (under `modules/admin/`) listing applications stuck in `SUBMITTING`/`SUBMISSION_OUTCOME_UNKNOWN` beyond an expected window, for manual investigation per the `AJA-PROD-008` policy.

3. **`AJA-PERF-001`** — Timeouts, rate limits, and async budgets.
   Define and enforce latency budgets for the plan-generation and AI-generation paths (these must not block the request thread indefinitely) and email-send path; add rate limiting where a channel (e.g. Lever's API) requires it.

4. **`AJA-QA-001`** — P0/P1 test pyramid.
   Ensure unit/integration coverage exists for: eligibility engine, answer library, planner idempotency, consent enforcement, autopilot rule limits, channel detection, duplicate prevention (DB + service + queue layers), queue/worker idempotency, unknown-outcome handling.

5. **`AJA-QA-002`** — E2E happy paths.
   End-to-end tests for the Assisted-Apply and Email-Apply flows, start to finish.

6. **`AJA-QA-003`** — Failure injection.
   Deliberately inject: submission timeout after employer acceptance (must classify `UNKNOWN`, never auto-retry), duplicate submission attempts (must be blocked at every layer), consent revoked mid-flight (must halt).

7. **`AJA-QA-004`** — Accessibility tests for review/consent UI.
   The Wave 3 review/approval UI and Wave 2/6 consent UI must pass accessibility testing — these are consent-bearing surfaces, not decorative ones.

8. **`AJA-UI-004`** _(P3, nice-to-have)_ — Deep-linkable application detail route.
   The tracker detail view is currently modal-only; add a real route so application detail pages can be linked/bookmarked/shared.

## Definition of done — full acceptance checklist

Pulled from `22-production-acceptance-checklist.md`; check every row against whatever scope has shipped (Wave 4 = email/external MVP; Wave 5 = + browser; Wave 6 = + ATS/autopilot). Checked below only where the shipped scope (Waves 1–4's `EXTERNAL_MANUAL` channel, no email/ATS/browser/autopilot) is both built AND has a passing automated test proving it — unbuilt-scope rows stay unchecked with a reason rather than being marked "N/A as satisfied," to avoid the exact false-capability-signal this feature is built to prevent:

- [x] Never submits without authorization + consent. — `SubmissionOrchestrationService.approve()` requires an active `RESUME_USAGE` grant; `SubmissionProcessingService.processJob()` re-checks it immediately before every submit. Tested.
- [x] Users access only their own profiles/answers/resumes/plans/applications. — IDOR suite across all 13 resource `*.security.api.test.ts` files.
- [ ] AI never invents factual candidate information. — Not applicable yet: `AJA-AI-001`/`AJA-AI-002` (cover-letter/screening-answer generation) are unbuilt; the planner reports `contentGenerationAvailable: false` rather than fabricating output.
- [x] Unknown answers always become `USER_INPUT_REQUIRED`. — planner returns `INFORMATION_REQUIRED` + `unresolvedQuestions` for baseline keys with no verified answer. Tested.
- [x] Sensitive answers are never auto-generated or auto-submitted. — `autoSubmitAllowed` is force-set `false` for every `SENSITIVE_QUESTION_KEYS` entry, both on create and on update; `PROHIBITED_QUESTION_KEYS` reject outright. Tested.
- [x] Eligibility is evaluated independently of recommendation match score. — `EligibilityService` never imports `modules/recommendations`. Tested.
- [x] Job status, rules, and consent are all revalidated immediately before every submit. — `SubmissionProcessingService.processJob()` re-checks job-active and consent right before calling the adapter, not just at approval time. Tested (including the consent-revoked-mid-flight e2e case).
- [ ] Daily/weekly limits are enforced (if autopilot shipped). — Autopilot is unbuilt (Wave 6, blocked on a real ATS/partnership decision); `ApplicationRuleService.setPaused` exists as forward-compatible infra only.
- [x] Duplicates are blocked at the DB, service, and queue layers. — DB: `PrismaJobApplicationRepository` unique constraints + `P2002` remap (now tested). Service: exact/canonical/fuzzy checks in `JobApplicationService.initiate` (tested). Queue: `claimForSubmission`'s atomic guard (tested at both the service-mock and now the repository level).
- [x] Workers are idempotent; `SUBMISSION_OUTCOME_UNKNOWN` is never auto-retried. — Redelivery/racing-workers failure-injection tests; `retry()` only allows a prior `FAILED_SAFE_TO_RETRY` outcome, never `UNKNOWN`.
- [x] State transitions are validated; recruitment status and submission status remain independent. — `state-machine.util.ts`'s validated graph; `JobApplication` is a wholly separate model from the recruitment `Application`.
- [ ] Plans are versioned, expire, and snapshot their inputs. — Versioned and input-hash-snapshotted (`planVersion`/`planInputsHash`, tested via the idempotent-replan case); there is no actual plan expiry/TTL implemented, so this line is only partially satisfied.
- [ ] Emails only go to vacancy-associated addresses; OAuth tokens are encrypted and revocable. — Email channel is unbuilt (`AJA-EMAIL-001` Gmail OAuth on hold, no credentials); `VacancyEmailDiscoveryService` extraction logic exists but is not wired into a live send path.
- [x] External URLs are validated (http/https only) everywhere they're opened or stored. — `JobChannelSnapshot.applyUrl`/`JobEligibilitySnapshot` are only ever populated from already-validated http(s) job-source URLs; `ExternalRedirectAdapter` refuses to submit without one.
- [ ] Browser packages (if shipped) are signed, expiring, and user-scoped. — Not shipped (Wave 5, blocked — separate extension codebase).
- [ ] ATS submission (if shipped) is restricted to authorized partners only. — Not shipped (Wave 6, blocked — needs a real partnership).
- [x] No CAPTCHA/MFA/anti-bot bypass exists anywhere in the system. — `shared/security/auto-apply-policy.ts` codifies the prohibition; no adapter touches a third-party form at all (`ExternalRedirectAdapter` only hands off a URL).
- [ ] The full UI state matrix (loading/empty/error/information-required/review/approval/queued/submitting/success/failed/unknown) is implemented, not just the happy path. — Most states have a distinct chip/action in `SubmissionsTab`, but this wasn't formally audited state-by-state against the matrix, so it stays unchecked rather than assumed.
- [x] An audit timeline and observability metrics exist for the full plan → submit → outcome lifecycle. — `AutoApplyAuditEvent` + `GET /auto-apply/events`, recorded at every stage from `PLAN_CREATED` through `SUBMISSION_SUCCEEDED`/`FAILED`/`OUTCOME_UNKNOWN`.
- [x] P0/P1 automated tests are green. — 712 backend tests passing; taxonomy audited against this ticket's own list this pass (`AJA-QA-001`), one real gap found and closed.
