# Auto Job Apply — Overview & Product Decisions

> Source material this roadmap is derived from: `zip/auto-job-apply-production-analysis/` (24 files: architecture, gap/risk matrix, target design, DB/API/security/perf/testing analyses, roadmap, acceptance checklist) and `zip/auto-job-apply-production-tickets/` (49 tickets across 18 epic files, dependency map, release waves, product decisions). Those files remain the source of truth for detailed acceptance criteria per ticket — this folder sequences and adapts them to the actual codebase; it does not duplicate them.

## Why this exists

Career Copilot's `application-management` module (`backend/src/modules/application-management/`, mounted at `/api/v1/applications`) is a solid, fully-implemented **manual application tracker**: CRUD, saved jobs, notes/tasks, status history, IDOR-tested. It has **zero automated "apply" capability** — no eligibility checking, no verified-answer library, no AI-generated cover letters/answers, no submission channels, no approval workflow, no queue. The "Apply Now" button on job cards just opens the external URL in a new tab; it never touches the tracker.

An analysis pass produced a full production-readiness audit: 56 concrete gaps (20 P0) between what exists and a genuine auto-apply system, plus a target architecture and a 49-ticket backlog. That material intentionally made **no code, schema, or product decisions** — every decision was left open, and the design's core constraint was stated repeatedly:

> This must not be an uncontrolled bot that applies everywhere. The system finds jobs, prepares an application, the user reviews/approves it (or pre-authorizes it under strict rules), and only then does an approved channel submit it — with confirmation and failure states tracked honestly.

This folder turns that analysis into an executable, wave-by-wave roadmap grounded in the real codebase, so each wave (`wave-1-*.md` … `wave-7-*.md`) can be handed to a separate execution agent on its own, without that agent re-reading all 76 source files first.

## Product decisions (locked in)

The reference material's 8 product-decision tickets (`AJA-PROD-001..008`) are resolved here using its own stated recommendations, accepted as-is. **These are binding** — no ticket in Wave 2 or later should re-litigate them without a deliberate change to this document.

| #              | Decision                                | Locked answer                                                                                                                                                                                                                                                                                            |
| -------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AJA-PROD-001` | Initial application modes               | **Assisted Apply + Approval-based auto-apply** for MVP (Waves 1–4). Full Autopilot (Mode C) is deferred to Wave 6 and gated by its own rules ticket (`AJA-RULE-002`).                                                                                                                                    |
| `AJA-PROD-002` | Allowed application channels            | **External Manual + Email** for MVP (Wave 4). Browser-assisted apply in Wave 5. Authorized/partner ATS only in Wave 6 — **never** inferred from ATS URL pattern-matching (Greenhouse/Lever/Ashby are ingest-only providers today, not submission-authorized).                                            |
| `AJA-PROD-003` | Autopilot limits policy                 | **≤5 applications/day**, minimum match score **0.85**, email + authorized-ATS channels only, mandatory pause control.                                                                                                                                                                                    |
| `AJA-PROD-004` | Email sender model                      | **Connected user mailbox** (Gmail OAuth 2.0) — draft-first: user reviews the first N generated applications, then can enable rule-based auto-send once trusted. Never a shared platform mailbox for outbound applications.                                                                               |
| `AJA-PROD-005` | Sensitive screening-answer policy       | Demographic / disability / veteran-status questions: **never auto-answer, never store**. Work-authorization, salary, notice-period: may be stored as verified answers **only with explicit per-field user consent** and a `USER_VERIFIED` source.                                                        |
| `AJA-PROD-006` | Submission vs. recruitment status model | **Separate `JobApplication` submission entity** + attempt model, kept apart from the existing recruitment-tracking `Application` entity. Avoids corrupting tracker/analytics semantics that already work today.                                                                                          |
| `AJA-PROD-007` | Duplicate-job policy                    | Hard DB-level block on `(userId, jobId)` and `(userId, normalisedJobUrl)`; canonical-job-id matching as a second hard check; fuzzy company+title+location match is a **warning only**; user override only ever applies to manual tracking, **never** to autopilot.                                       |
| `AJA-PROD-008` | Unknown submission outcome policy       | **Manual investigation + user-confirmation** by default; provider-native confirmation polling/reconciliation where a channel supports it; **never auto-resubmit** a `SUBMISSION_OUTCOME_UNKNOWN` — a blind retry could create a duplicate application after a submission the employer actually received. |

## Target architecture (shared services)

These are the building blocks every wave contributes to. None of them exist yet except the tracker.

- **Candidate Application Profile** — structured, apply-specific profile (personal info, employment/education/skills, preferences, links, verification metadata) distinct from resume-parsed data. Built by extending the existing `CandidateProfile` model.
- **Verified Answer Library** — canonical question-key catalog of user-verified answers (work auth, sponsorship, notice period, salary, relocation, etc.), each carrying source, `lastVerifiedAt`, sensitivity flag, and `autoSubmitAllowed`. AI must never invent these; unknowns become `USER_INPUT_REQUIRED`.
- **Eligibility / Rule Engine** — hard pass/fail checks (auth, sponsorship, location, salary floor, blacklist, limits) run at apply-time, explicitly separate from recommendation match scoring. A 92%-match job can still be ineligible.
- **Application Planner** — `ApplicationPlannerService.createPlan()`, idempotent, combining eligibility + channel + resume selection + generated content + answers into one versioned, expiring plan with an explicit readiness decision.
- **Channel Detector** — classifies each job as `ATS_API_AUTHORIZED | EMAIL_SUPPORTED | BROWSER_ASSISTED | EXTERNAL_MANUAL | UNSUPPORTED` without assuming authorization from URL pattern alone.
- **Resume / Cover-Letter / Screening generation** — job-specific content generation, grounded in verified profile data, confidence-scored, never fabricating facts.
- **Adapter Registry** — `JobApplicationAdapter` interface (`inspect/validate/submit/getStatus`) with per-channel implementations behind feature flags.
- **Submission Queue** — RabbitMQ-based prepare/submit/retry pipeline with locking, revalidation, and a `FAILED_SAFE_TO_RETRY` / `FAILED_DO_NOT_RETRY` / `SUBMISSION_OUTCOME_UNKNOWN` taxonomy. Never auto-retries `UNKNOWN`.
- **Consent Service** — versioned, explicit `ApplicationConsent`, required before email/ATS/autopilot use; revocable at any time.
- **Audit / Observability** — event trail and metrics for every plan, approval, submission, and outcome.

## Repo conventions every wave must follow

- **Module ownership**: build only inside `backend/src/modules/application-management/` or new sibling modules under `backend/src/modules/`. `backend/src/modules/applications/` is dead stub code (unreferenced by `routes.ts` or anything else) — removed in Wave 1, do not resurrect it.
- **Naming collision to avoid**: `backend/prisma/resumes.prisma` already defines a `ResumeVersion` model — that's the _resume-builder tailoring_ concept (tied to `ResumeAnalysis.id`, fields `label`/`content`/`atsScore`). The Wave 2 "approved resume version selectable for auto-apply" concept must use a **different name** (`ApprovedResumeVersion`) to avoid clashing.
- **`CandidateProfile`** (`resumes.prisma`, unique per `userId`, JSON blobs for personal/experience/education/skills/certifications) is the existing onboarding profile. Extend it in place with apply-specific columns/JSON (preferences, links, field verification metadata) rather than creating a duplicate parallel identity model.
- **Queueing is RabbitMQ**, via the custom `messageBus` abstraction in `backend/src/infrastructure/messaging/` (topology in `messaging.topology.ts`: `MessageExchanges`, `MessageQueues`, `MessageRoutingKeys`, `QoSPresets`) — **not BullMQ**. New submission queues must mirror the existing producer/consumer split: `backend/src/queues/email.queue.ts` (typed job union, `messageBus.publishEvent(exchange, routingKey, job)`, fire-and-forget from the request path) and `backend/src/workers/email.worker.ts` (`messageBus.subscribe(...)` with a `QoSPresets` entry, run as an independent process via a `run-*-worker.ts` entrypoint).
- **RBAC**: add new permission keys to `backend/src/shared/rbac/permission.catalog.ts` following the existing `<resource>.<action>.own` convention (e.g. `applications.autoapply.create.own`), add the matching `PermissionDefinition` entry, and chain `authMiddleware, requirePrincipalType('USER'), requirePermission(...)` on every new route — exactly as `application-management/routes/application.route.ts` already does. New "own"-scoped keys are automatically granted to the `USER` role via `ROLE_PERMISSION_MAP`.
- **Prisma is multi-file**: each domain owns its own `backend/prisma/*.prisma` file, merged at build time (see `prisma.config.ts`). New auto-apply models belong in a new file (e.g. `backend/prisma/job-applications.prisma`), not appended to `applications.prisma`.
- **`notifications` module is also a stub** today (same dead-TODO pattern the old `applications` module had). Wave 4+ submission-result notifications will need it built out, or can use `EmailQueue` directly as an interim measure.
- **IDOR/authz test template**: `application-management/__tests__/application.security.api.test.ts` is the pattern every new endpoint's tests must match — 401 for unauthenticated calls, cross-user access returns 403/404 with no data leakage, no `userId`/`x-user-id` request-spoofing. Apply this to every new resource type from Wave 2 onward.
